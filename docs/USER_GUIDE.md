# 流量哨兵 fnnetmon

飞牛 fnOS 原生 `.fpk` 应用，对标 Little Snitch：
**按应用和服务排行网络流量，一眼看出谁在偷跑**；每个连接直接显示域名、归属地和运营方，
记录每个程序第一次连了哪里，并可按进程或域名拦截出向访问。

安装包按架构分开：

| 平台 | 文件 | 大小 |
| --- | --- | --- |
| ARM（飞牛 ARM 机型） | `pkg/fnnetmon_0.9.9_arm.fpk` | 11.76 MB |
| x86_64（飞牛 x86 机型） | `pkg/fnnetmon_0.9.9_x86.fpk` | 12.09 MB |

装错架构会在安装或启动时直接报错，装之前对一下「系统信息 → 处理器型号」：
带 x86 字样的是 x86_64，带 aarch 的是 ARM。

这 11.75 MB 里，程序本体压缩后占 4.7 MB，内置的 GeoLite2 国家 + ASN 库占 6.9 MB——
库比程序大是正常的。x86 版比 ARM 版大 344 KB，来自 Go 在 amd64 上生成的机器码本身就更大。
省市级数据（City 库，48 MB）不再内置——需要时在界面「域名归因」卡片上点一下「安装省市数据」，
装完直接生效、不用重启；也可以用命令行装，见「地理和 ASN 数据」。

容器、历史、告警、拦截和主题收在「更多」里；图表支持手指拖动查看数值。

数据每秒刷新一次，采集口径：

- **连接字节**：内核 `tcp_info` 的 `tcpi_bytes_acked` / `tcpi_bytes_received`（netlink `inet_diag` 读取），TCP 精确；
- **网卡速率**：`/sys/class/net/*/statistics`；
- **进程归因**：socket inode → `/proc/<pid>/fd` → 进程，5 秒全量刷新（实测 60ms）；
- **容器归因**：cgroup + 容器内 eth0 的 `iflink` → 宿主机 veth，精确到容器。

三个口径对不上是常态，所以界面上把差额显式画出来了，见下一节。

### 回环和「未归因」：为什么排行加起来不等于网卡总量

三个口径天生对不上。硬凑成一个数只会得出错误结论，所以分开记账。

**本机回环不参与统计。** `127.0.0.1` / `::1` 上的连接不经过网卡，是进程之间的 IPC。
更要紧的是：一个回环连接在宿主机上有**两个** socket（客户端和服务端各一个），字节数互为镜像
——A 的发送量正是 B 的接收量。两端都记，排行里就会出现两行合计完全相同、各占 50.0% 的条目，
而它们其实只是一次本机转发。现在只按本地端口较大的一端记账，并整体从排行里剥离；
连接页仍能看到，带「本机」标签，默认折叠。

**「未归因」是一个正式的条目。** 它等于网卡总量减去已归因的部分，来源有四类：

| 来源 | 为什么抓不到 |
| --- | --- |
| UDP | `inet_diag` 对 UDP 不返回字节计数，只有连接数 |
| 容器 | socket 在独立 netns，宿主机 `sock_diag` 看不到，只能走 veth 统计 |
| 无主 socket | inode 找不到持有它的进程（进程刚退出，或 socket 在别的 netns） |
| 内核态 | 转发、隧道、ARP / ICMP 这类根本不经过 socket |

差额大不是 bug，是这个工具的能力边界。**把它藏起来才是 bug**：网卡跑着 400 KB/s、
排行里最高只有 4 KB/s，用户会以为一切正常，而这正是「谁在偷跑流量」最该回答的时刻。
所以「未归因」在概览首屏和排行里都占一行，带虚线问号图标，排在它该在的位置上。

**光说「有 760 KB/s 找不到主人」不够，所以加了下钻。** 后台挂一张只读的 nftables 统计表
（`table inet fnnetmon_stat`，`output` / `forward` 链各挂一个 `counter`，`policy accept`，
**一条 drop 规则都没有**），每 5 秒采一次，于是「未归因」被拆成三份：

| 分项 | 来源 | 说明 |
| --- | --- | --- |
| **UDP** | `output` 链的 udp 计数器 | 有字节数、没主人，是 UDP 缺口的准确值 |
| **内核转发** | `forward` 链计数器 | 网桥、容器 NAT、隧道，根本不经过本机 socket |
| **其余** | 总量减去上面两项 | 无主 socket 和内核态产生的流量 |

统计表是**独立的一张表**，和拦截用的 `table inet fnnetmon` 完全分开：采集失败、
nft 版本不认这些语法，最坏结果是这一栏不显示（界面回落到「找不到主人的流量」一句话），
不会影响排行、历史、拦截里的任何功能。

> **0.9.8 修的坑**：链名不能叫 `fwd`。nft 的 lexer 把 `fwd` 当关键字（`fwd to <dev>`），
> `chain fwd` 直接报 `syntax error, unexpected fwd, expecting string`，
> 日志里表现为一行 `unattr breakdown off: ...`。这个错从 0.9.0 就有，两个架构都一样，
> 只是以前没人翻 server.log。现在链名统一加 `fnm_` 前缀，读计数器只认
> `counter comment`（`"tcp"` / `"udp"` / `"fwd"`），旧表不重建也能继续读；
> 建表按「出向 + 转发 → 仅出向」逐级降级，表存在但没计数器会删掉重建，
> 失败后每分钟自动重试，不会再一次性静默关掉。

### 历史数据怎么存的

本地 SQLite（`/var/apps/fnnetmon/var/db/fnnetmon.db`，WAL 模式），纯 Go 驱动，不需要 cgo。

- 每秒的增量累加进**分钟桶**，跨分钟时一个事务批量落盘；进程退出前（SIGTERM）会把当前分钟补写一次，重启不丢最后一分钟；
- 每 5 分钟做一次 `1m → 1h → 1d` 滚动汇总，所以 7d / 30d 视图不需要扫全表；
- 保留期：分钟级 7 天、小时级 90 天、天级 400 天，每小时清理一次。稳态下整库不到 100 MB；
- 时间桶按**本地时区**对齐，「按天」的边界是本地 00:00，不是 UTC 00:00；
- 图里只画 Top 8 序列，剩下的合并成「其他」，避免几十个进程把图糊掉。

**历史页默认按「应用」看，不是按进程。** 原因很直接：`pxy`、`node`、`next-server (v1)` 这些进程名
回答不了「这个月谁在偷跑流量」，用户是按「飞牛影视」「百度网盘」定位的。所以默认维度是应用：

- 进程维度的 key 经 `Hub.ProcServices()` 归并回服务名（应用中心装的用 `display_name`，
  系统服务用 systemd 单元名）；
- 容器流量按**容器名**成行，并标一个「容器」标签——容器在独立 netns 里，宿主机看不到它的 socket，
  这部分只存在于容器维度，和进程维度不会重复计算；
- 一个应用挂多个进程（node + ffmpeg 都属于「影视」）时，**同一个时间桶里要累加**，不是取最后一个；
- 已经退出、当前快照里查不到归属的进程，按它自己的名字单独成行——丢掉的话历史总量会少一块，
  用户会以为是采集漏了。

**库里仍然只存进程维度**，应用是查询时归并出来的。另存一份会让 `agg` 表体积接近翻倍，
而 4GB 内存的机器上 eMMC 写入和 DB 体积都是有预算的。代价是「进程退出后归并不回去」这个近似，
对「谁在偷跑」够用——真正偷跑的服务进程通常是常驻的。想细看进程就切「进程」按钮。

历史视图支持 URL 参数，方便直接定位：`?range=7d&dim=svc&dir=rx#hist`。

CSV 导出带 UTF-8 BOM，Excel 双击打开不乱码。两个口径：

- **历史页**导时序明细，一行一个时间点：`时间,维度,名称,下行字节,上行字节,下行MB,上行MB`，
  维度是应用时名称就是应用名（同一时间点多个进程已合并成一行）；
- **排行页**导区间汇总，一行一个服务：`排名,名称,维度,下行字节,上行字节,合计字节,下行MB,上行MB,占比%`，
  写周报直接贴。

下行在前的顺序和界面上的 ↓ / ↑ 一致，不用心算对齐。数据是边查边写的（不先拼成一个字符串），
30 天的量也不会把内存顶起来。

### 首次外联是怎么判断的

主键是 **`(进程, 远端 IP)`**，不是连接。同一个程序连同一台主机的不同端口算同一条对端——
否则一个浏览器开十个标签页就会刷出十条「新外联」，完全没法用。

- 只记**有明确进程归属**的连接。TIME_WAIT 和「无主 socket」跳过，因为拿不到 cgroup，记了也没法生成规则；
- 回环地址（`127.0.0.1` / `::1`）不记，噪音太大；
- 内网地址会记，但**默认不在列表里显示**，需要勾「包含内网」才看得到；
- 「连接次数」只统计新建连接，不是采样次数——后者会等于「活跃秒数」，没有意义；
- 记录存在 SQLite 的 `peer` 表，重启不丢；「首次见到」的时间一旦写下就不会被覆盖。

### 服务归因是怎么做的

「排行」页默认按服务聚合，而不是按进程名。原因很直接：一个应用常常挂着十几个进程
（`node`、`python3`、`ffmpeg`、`transmission-daemon`），按进程名看是一屏噪音，
而用户想知道的是「哪个应用在偷跑」。

服务归属按优先级取：

1. **应用目录** —— 可执行文件路径里出现 `@appcenter` / `@appstore` 这一段（后面紧跟应用名），
   或者落在 `/var/apps/<应用>/` 下，就归到那个应用；
2. **systemd 单元名** —— 取 cgroup 路径里**第一个** `.service` 段，比如
   `/system.slice/trim-media.service/ffmpeg.scope` → `trim-media`。
   取第一段而不是最后一段，因为子作用域挂服务下面，最后一段是内部 scope，拿来当服务名没有意义；
3. **可执行文件名** —— 前两条都不成立时的兜底。

**这里踩过一个很深的坑**：`/proc/<pid>/exe` 读到的是**软链解析后**的真实路径。
`/var/apps/<包名>/target` 恰恰是一个指向 `/usr/local/apps/@appcenter/<包名>` 的软链，
所以官方应用的 exe 全都是 `/usr/local/apps/@appcenter/trim.photos/trim-photos` 这种形状。
早期版本只认 `/var/apps/` 前缀，结果**一个官方应用都匹配不上**，全部落到 systemd 单元名
（`trim_app_center`）或者可执行文件名（`trim-photos`）上——这就是界面上那些 `trim.xxx` 的来历。
现在按路径段判断，装到存储卷上的应用（`/vol1/@appcenter/...`）也一并认了。

服务名本身有四个来源，按权威程度排：

| 顺序 | 来源 | 说明 |
|---|---|---|
| 1 | `appcenter-cli list` | 应用中心自己维护的已装列表，最权威；后台每 5 分钟问一次 |
| 2 | `manifest` 的 `display_name` | 应用中心里显示的名字 |
| 3 | `app/ui/config` 的 `title` | 桌面入口的名字，manifest 缺 `display_name` 时的替补 |
| 4 | 内置对照表（`appnames.go`） | 前三条都读不到时用，178 个条目 |

两个容易忽略的细节：

- **`manifest` 的值经常带引号**。官方文档的示例是裸值（`appname=HelloFnos`），
  但真机上大量写成 `display_name="音乐"`。不去引号的话界面上会显示成带引号的名字；
- **`appname` 不是展示名**。官方文档写的是「应用唯一标识」，它经常就等于目录名，
  拿它当名字等于什么都没读到。所以它排在入口 `title` 后面，而且只在和包名不同时才用。

另外两个刻意的取舍：

- **容器内进程一律归到容器名下**，不拆到进程。容器 socket 在独立 netns，宿主机本来也看不到；
- **`session-N.scope` 这类登录会话不当作服务**，否则 SSH 里跑的临时命令会各自变成一行。

同一进程名在不同服务下不再被合并（内部 key 是「服务 + 进程」），
所以「影视的 node」和「Node.js v24 的 node」会是两行。

**核对服务名：`fnnetmon svc`**

上面四条来源都要在真机上才读得到，任何一环读不出来名字就会**静默回落**，
界面上只会显示成 `trim.xxx`，不会报错。这条命令把每个应用实际解析出什么、
依据是哪一档、以及应用中心自己怎么叫它，并排列出来：

```bash
$BIN svc            # 表格，回落过的行标 ⚠，两边不一致的标 ≠
$BIN svc --json     # 结构化输出，方便贴出来对照
$BIN svc --no-cli   # 不调用 appcenter-cli，只看本地文件
```

```
应用根目录 /var/apps（31 个应用）
应用中心：31 个已装应用

  包名                          本地读到的名字          依据            应用中心
  trim.music                    音乐                    display_name    音乐
  trim.baidunetdisk             百度网盘                display_name    百度网盘
  trim.someapp                  trim.someapp            缺 manifest     trim.someapp  ⚠
```

标 ⚠ 的行是名字没从 `display_name` 读出来的，标 ≠ 的行是本地 manifest 和应用中心不一致的
——后者才是真正该去改 manifest 的地方。开发机上没有 `/var/apps` 会直接提示，不会假装成功。

### 排行的时间口径

- **实时** 直接用 `/api/snapshot` 算，每秒刷新；
- **1 小时 / 24 小时 / 7 天** 走 `/api/rank`，从历史库按进程维度汇总后归并到服务。
  历史库只存了进程维度，服务维度在查询时归并——多存一份会让 `agg` 表体积接近翻倍，
  而 4GB 机器的 eMMC 写入和 DB 体积都是有预算的。

已知近似：进程退出后就不在当前快照里了，归并时查不到映射，会按它自己的名字单独列出。
对「谁在偷跑」这个问题够用——真正偷跑的服务进程通常是常驻的。

### 域名归因是怎么做的

用的是 **AF_PACKET 抓 DNS 应答**，不是 TLS SNI，也没有走 eBPF。

理由是成本差两个数量级：eBPF 要 clang 交叉编译、要 attach tc hook，而且只能覆盖 TLS。
只解析 DNS 应答里的 A/AAAA 记录，HTTP、QUIC、MQTT、游戏私有协议全都能归因。

- 一个未绑定的 `AF_PACKET` socket 收所有网卡的包，设了 `SO_RCVTIMEO`（和 netlink 一样的坑，没超时会永久卡死）；
- 只处理 UDP 53 端口的应答报文（`QR=1`、`rcode=0`），畸形报文一律丢弃，解析器有长度和跳转次数上限；
- 同时维护 **IP→域名** 和 **域名→IP** 两张表，前者用于界面展示，后者用于把域名规则翻译成 nft 里的地址集合；
- TTL 取应答里最短的那个，夹在 60~3600 秒之间；IP→域名表上限 8192 条，域名表 4096 条，超了淘汰最快过期的；
- 同一个 IP 被多个域名解析到（CDN 常态）时保留最早见到的，另外记一个计数，界面显示「a.com +2」。

**已知缺口**：Chrome / Firefox 默认开 DoH，DNS 包不经过网卡，这部分归因不到。
补法是抓 443 明文 ClientHello 里的 `server_name`，但那是另一个量级的复杂度，先不做。

### 地理和 ASN 数据

**国家与运营方内置，装上就能用。** 两个库随 fpk 一起分发：

| 文件 | 大小 | 内容 |
| --- | --- | --- |
| `GeoLite2-Country.mmdb` | 3.2 MB | 国家 |
| `GeoLite2-ASN.mmdb` | 8.6 MB | 自治系统号与运营方 |

**省市级数据按需安装。** `GeoLite2-City.mmdb` 有 48 MB（打包后 25 MB），
对 4GB 内存的 NAS 来说占了安装包三分之二，而多数人只想知道「连的是哪国的谁」。
所以它不进安装包。最省事的是在界面里装——概览页「域名归因」卡片上直接点：

- 没装：「安装省市数据 · 约 48MB，装完不用重启」→ 点下去就地显示进度条（`18.0 / 48.0 MB（37%）`）
- 已装：「国家 + 省市」+「删除省市数据 · 省出约 48MB」

**装完是热加载的**：重扫目录、换 reader、清掉旧的查询缓存，不用重启进程。
（缓存必须清，否则同一个 IP 还会显示旧库里的城市名。）

命令行也可以：

```bash
BIN=/var/apps/fnnetmon/target/bin/fnnetmon

$BIN geo status              # 现在用的是哪些库、有没有城市级、构建日期
$BIN geo fetch               # 从 GitHub 镜像下载 City 库并装上（约 48 MB，几分钟）
$BIN geo install /tmp/GeoLite2-City.mmdb   # 或者自己传一个上去
$BIN geo remove              # 不想要了，删掉，回到只有国家
```

装上之后，连接页和外联页的归属地会从「美国」变成「美国 · 洛杉矶」——
省市直接显示在行里，不用鼠标悬停（手机上没有悬停）。

`geo fetch` 走 `ghproxy.net` 镜像（官方下载站要 license key）。下载完会校验
`DatabaseType` 是不是 City 库，不是就不覆盖；写入用临时文件 + 原子替换，断电不会留下半个库。
安装目录是 `/vol1/@appdata/fnnetmon/geo/`，**不动程序目录**，所以升级 fpk 不会把它冲掉。

GeoLite2 以 **CC BY-SA 4.0** 发布，允许再分发，前提是署名并以相同许可共享——
署名文件在 `data/geo/NOTICE.txt`，会一起打进包。数据库内容未做任何修改。

扫描顺序是**数据目录优先、内置目录兜底**：想换新库，把 mmdb 丢进
`/vol1/@appdata/fnnetmon/geo/`（或直接丢进 `/vol1/@appdata/fnnetmon/`）就行，不用重新打包。
同一个目录里 City 优先于 Country（City 是 Country 的超集，还多了城市名）。

数据库走 mmap：只有真正查到的页会变驻留，不会一启动就把 60 MB 全读进内存。
驻留的那部分确实会计入 `VmRSS`，所以自检里 RSS 的**预算判定**先把 `.mmdb` 映射扣掉
（读 `/proc/self/smaps` 单独统计），否则「装了个大库」和「内存慢慢泄漏」在数字上没法区分。
界面上显示的还是真实 RSS，只是备注里写清楚其中多少是可回收的映射页。

### 列表点击为什么不跳动

连接页一秒刷一次。原来每次都是 `innerHTML` 重建整张表，于是点「展开分组」后：
新表把行重新排一遍，你刚看到的那行往上或往下跑了，得重新找——手机上尤其烦。
外联页裁决、排行页展开同理。

现在做两件事：

1. **结构没变就不重建。** 每秒算一个只含成员（不含数值、不含展开状态）的指纹；
   指纹相同就原地改那几个数字单元格。行序稳定，节点不换，hover 和正在选中的文字都不会断。
   刚点过 2.5 秒、鼠标停在表上、或者正在选文字时，一律不重建。
2. **真要重建就把锚点钉住。** 改 DOM 前后各量一次目标行的位置，差值用 `scrollBy` 补回来。
   节点被换掉的情况（比如裁决后那一行消失了），就按「第几行」在新表里找回来，
   让顶替它位置的那一行停在原地。

不是禁用滚动——你自己滚还是照常滚，只是「点了不该动」的时候它不动。

### 字号、配色和「卡片别空着」

界面上容易显得毛糙的三件事，都定成了硬规则：

**字号只有五档。** 10 徽标 / 11 辅助 / 12 正文 / 13 基础 / 14+ 标题与数值。
之前是 9.5、10、10.5、11、11.5、12.5、13.5 七档混着用，同一个「副行」
（进程名、路径、时间戳）在 KPI 卡、表格、图例里能出现三种大小。
规则写在 `dashboard.html` 的 CSS 开头，改字号只改那一处注释。

**KPI 卡片不留空。** 网格会把并排的卡片拉到一样高，所以「只有一个数字」的卡片
底部必然空出一截。现在每张 KPI 卡都是 flex 列，主指标在上、次要内容用
`margin-top:auto` 贴底：速率卡贴的是趋势线，连接卡贴的是一行事实
（无主 socket / veth 已映射 / UDP 无计数）。原本这些数据挤在副行里，
挪下来正好把高度填满，信息还更多。

**历史页颜色按排名固定，不循环。** 原来十色循环，第三条、第七条、第十条全挤在
青绿一段，三条曲线在图例里分不出来。现在分三档：前 3 名高饱和强调色
（蓝 / 橙 / 紫），4–6 名换色相降饱和（青绿 / 金 / 玫红），第 7 名以后才转中性灰
——这一档通常只占 1–2%，在图上本来就是细边，用灰退到背景里正合适。
全表只有一个绿。深色主题另有一套（灰阶往亮处挪），`applyTheme` 里会重画 canvas，
否则切主题后曲线还是浅色那套。

**窄屏上锁单行。** 名字、路径、副行说明一律 `nowrap` + 省略号，完整内容进 `title`。
允许换行的话，320px 下 `transmission-daemon` 占两行、`容器 · veth5e8a24e` 占三行，
排行页一张卡从 78px 长到 159px，一屏只剩两个半——而这一页存在的意义就是一眼扫完。
同理，`.toprates` 这类「右边那撮数字」必须 `flex:none`，否则会被 flex 压到比内容还窄，
数字直接溢出到左边的名字上。

### 流量告警

没人会一直盯着页面。「谁在偷跑」的下一步是「偷跑的时候告诉我」。

配置在「告警」页：填一个 Webhook 地址、打开开关、加规则。规则只有两个参数有意义：

- **匹配**：服务名或进程名，留空表示所有流量；
- **阈值**：速率模式填 KB/s（当前瞬时速度），累计模式填 MB（窗口内累计字节）。

冷却时间默认 30 分钟——同一条规则触发后静默，否则一个持续超标的进程会每分钟推一条。

推送格式按 Webhook 域名自动判断，不用记三种 JSON 结构：

| 地址包含 | 格式 |
| --- | --- |
| `qyapi.weixin.qq.com` | 企业微信群机器人 |
| `dingtalk` | 钉钉群机器人 |
| `slack.com` | Slack Incoming Webhook |
| 其它 | 通用 `{"text":"…"}` |

两个刻意的取舍：**评估在本地做**，只有触发时才往外发一句话，不把任何流量明细发出去；
**发送在采集锁之外**，Webhook 卡住 10 秒也不会拖慢每秒一次的采集。
企业微信和钉钉出错时仍返回 HTTP 200，错误码在 body 里，所以发送后会检查 `errcode`，
失败会记在「最近触发」的「推送」列上，鼠标悬停看原因。

配置存在 `/vol1/@appdata/fnnetmon/alerts.json`，不塞 SQLite——数据库坏掉时告警设置还在。

### 出向拦截是怎么做的

基于 **nftables 的 `meta cgroup`**，不是按 PID。

原因是 PID 是瞬时值，进程一重启就失效；而 cgroup 路径（如 `/system.slice/trim-qbittorrent.service`）
在服务重启后依然稳定，规则可以长期有效。所以规则里存的是 **cgroup 路径**，下发时才解析成 inode。

**这一层默认是关的。** 打开后也只做三件事：

1. 只挂 `output` 链，`policy` 永远是 `accept`——失败方向必须是「全放行」；
2. 只操作自己建的 `table inet fnnetmon`，绝不碰系统已有的规则集；
3. 白名单硬编码在链首，**回环、私网段、组播、链路本地永远放行**。
   这条是安全底线：即使规则写错，SSH、fnOS 管理页、内网共享都不受影响。

每次下发前会先跑 `nft -c` 做语法校验，整表原子替换。规则里的 cgroup 路径如果已经不存在
（服务被卸载或改名），那条规则会被跳过并在页面上标红，而不是下发一条匹配不到任何东西的死规则。

**万一真的连不上了**，SSH 里任选一条：

```bash
nft delete table inet fnnetmon
# 或者
/var/apps/fnnetmon/target/bin/fnnetmon firewall off
```

第二条会同时把「已启用」的持久化开关关掉，避免重启后又被重新下发。

服务停止和卸载时都会自动清表，卸载脚本里还有一道 `nft delete` 兜底——
规则残留是最难排查的故障，不能指望进程自己善后。

**如果机器上没有 nft 命令**（fnOS 可能用的是 iptables），拦截页会直接显示「不可用」并说明原因，
「外联」页的「阻止」仍然会记录裁决，但不会真的断开连接。这种降级是显式的，不会假装成功。

已知限制（都是内核机制决定的，不是没做完）：

- **UDP 没有字节计数**：内核不为 UDP 维护累计字节，连接列表里 UDP 只显示状态；
- **容器内的连接不显示在「连接」列表**：容器的 socket 在独立 network namespace 里，宿主机的 `sock_diag` 看不到。
  所以「容器」标签改用宿主机侧 veth 的字节统计——**流量数字是精确的，含 UDP**，但没有连接明细；
- 「排行」和「连接」标签只包含宿主机进程。容器内进程的 socket 在独立 netns，宿主机看不到，
  所以容器流量统一走 veth 统计，并在「排行」里以「容器」标签单列一行；
- **外联只记 TCP/UDP 的出向对端**，且必须有进程归属。内核态发起的连接（如 NFS 客户端回写）看不到进程，不会被记录；
- **拦截不能按端口方向区分**：规则里的端口指的是**远端端口**；
- **改 cgroup 会让规则失配**：如果服务被 systemd 移动到别的 slice，规则会失效（页面上标红），需要重新生成。

容器连接明细需要逐个 netns 执行 setns 后再 dump，风险较高，排在稳定性验证之后。

「容器」标签里每个容器下方会显示它对应的宿主机 veth 名（如 `veth5e8a24e`）；
显示 <span style="color:#a32d2d">未映射</span> 表示没找到对应的 veth，此时流量一定为 0，属于需要排查的异常。

## 稳定性自检

概览页底部有「运行状态」卡片，也可以直接在 SSH 里跑：

```bash
/var/apps/fnnetmon/target/bin/fnnetmon selfcheck
```

输出长这样：

```
运行时
  RSS             23.6 MB
  其中地理库        9.1 MB（mmap，可回收）
  goroutine       9
  文件描述符       26
  堆 / 系统       2.0 MB / 12.0 MB

采集
  次数            86400
  最近 / 最慢     0.9ms / 4.2ms
  平均            0.8ms
  跟踪对象        进程 87 · 容器 6 · 连接 143

存储
  数据库          18.4 MB（WAL 0.3 MB）
  行数            1m 172800 · 1h 2160 · 1d 90
```

**怎么用**：装好后跑一次记下来，过三五天再跑一次对比。

判断标准（都是针对这台 4GB 设备定的预算）：

| 指标 | 预算 | 超了意味着什么 |
| --- | --- | --- |
| RSS | 60 MB（已扣掉地理库映射） | 连接数暴涨，或 SQLite 页缓存没释放 |
| goroutine | 100 | 有泄漏，重点看 DNS 反查和 netlink |
| 文件描述符 | 256 | 泄漏会让进程几天后打不开新文件 |
| 单次采集耗时 | 500 ms | 超过 1000 ms 会开始丢采样，速率显示偏低 |
| 数据库体积 | 100 MB | 保留期没生效，检查 Purge 是否在跑 |

**只有「只涨不落」才是问题。** 装了地理库之后 RSS 会长期停在 24~45 MB
（其中一多半是 mmdb 的映射页，内核随时可以回收），自检会把那部分单独列出来并
从预算里扣掉，判断时看扣完之后的数。扣完还在 60 MB 以上、而且三天不回落，那才是泄漏，
把两次输出发我。

加 `--json` 可以拿到机器可读格式，方便自己写脚本对比：

```bash
BIN=/var/apps/fnnetmon/target/bin/fnnetmon
$BIN selfcheck --json >> /tmp/fnnetmon-health.log
```

## 卸载后确认干净

fnOS 卸载会删掉程序目录，但下面几样要自己确认一遍。**第 2 条最重要**——
残留的 nft 规则会一直拦流量，而且不装这个应用根本查不出来：

```bash
# 1. 进程
pgrep -f "fnnetmon serve" || echo "OK: 无残留进程"

# 2. nft 规则表（有输出就要处理）—— 拦截表和统计表两张都要看
nft list tables | grep fnnetmon || echo "OK: 无残留规则"

# 3. 目录
ls /var/apps/fnnetmon/ 2>/dev/null || echo "OK: 目录已删"
```

如果第 2 条有输出，立刻执行：

```bash
nft delete table inet fnnetmon        # 拦截规则（会真的拦流量，先清这个）
nft delete table inet fnnetmon_stat   # 只读统计表（不拦流量，但会一直计数）
```

卸载脚本里已经带了这两步，正常情况下不会残留。列出这个是为了万一——
万一真的残留了，你知道怎么处理。

## 构建

```bash
./build.sh              # 只出 ARM（默认）
./build.sh amd64        # 只出 x86_64
./build.sh both         # 两个都出
```

交叉编译 + 生成图标 + 打包，产物在 `pkg/fnnetmon_<版本>_<平台>.fpk`
（平台只有 `arm` / `x86` 两种）。
两个架构各出各的文件——以前都写同一个 `fnnetmon.fpk`，出完 x86 就把 arm 覆盖了。
打包时临时改 manifest，打完立刻还原，仓库里那份始终是 `arm` / `aarch64`。

**`arch` 和 `platform` 必须一起改**，这是两个不同的字段：

| 字段 | arm 包 | x86 包 | 谁在用 |
| --- | --- | --- | --- |
| `arch` | `aarch64` | `x86_64` | **应用中心校验架构读的是它** |
| `platform` | `arm` | `x86` | 应用商店索引、社区惯例命名 |

`arch` 缺失时应用中心会按默认架构处理，所以两个字段都得写（0.9.5 的 x86 包只写了 `platform`）。

**另一处更隐蔽的坑在 `cmd/install_init`**：0.9.5 / 0.9.6 的这份脚本写死只放行
`aarch64|arm64`，x86 机器上直接 `exit 1`，并自己打印了一句
「本安装包仅支持 ARM64 设备，当前架构为 x86_64」——长得和系统提示一模一样，
当时正是据此把问题误判成 `arch` 字段，补了字段却没删这颗地雷，0.9.6 依然装不上。
现在改成读 `bin/fnnetmon` 的 ELF `e_machine`（偏移 18、2 字节小端：
`b700` = aarch64、`3e00` = x86-64）自适应，两个包共用同一份脚本，
读不到就放行、绝不误拒；`build.sh` 里也加了断言防止有人改回去。
真正装错架构时，`cmd/main` 的 start 还会因为进程起不来写日志。
开发机上工具链固定在 `tools/`（Go 1.27.3、fnpack 1.2.3）；源码包不带它们，会自动回落到系统工具，见下一节。

## 换机器继续开发

`fnnetmon-src_<版本>.tar.gz` 放在**项目上一级目录**（不进包自身），用
`python3 tools/make_src_bundle.py` 重新生成。解压后就是完整工程：

```bash
tar -xzf fnnetmon-src_0.9.9.tar.gz && cd fnnetmon
./build.sh both
```

新机器只需要：**Go 1.26+**、**python3**（只用标准库）、**能访问 Go 模块代理**
（首次会拉 `modernc.org/sqlite` 等依赖）。源码包不含 Go SDK、`tools/gocache`、
`tools/gopath`、`dist/` 和成品 fpk——这些加起来 1.5 GB，全都能重建。

`build.sh` 的解析顺序：

| 工具 | 顺序 |
| --- | --- |
| Go | `tools/go/bin/go` → `PATH` 里的 `go` |
| Python | `python3`；要指定用 `PYTHON=/path/to/python3 ./build.sh` |
| 打包 | macOS 且 `tools/fnpack` 可用 → `fnpack`；否则 `tools/fpk_pack.py` |

`fnpack` 是 macOS x86_64 二进制，Linux/Windows 用不了。`fpk_pack.py` 是纯 Python
等价实现（fpk 就是两层 tar.gz，manifest 里的 `checksum` 是 `app.tgz` 的 MD5），
产物已与 fnpack 逐项比对：条目、权限、文件内容、manifest 全一致。
`FNPACK=python ./build.sh` 可以强制走它。**它没在真机上安装验证过，
装包优先用 fnpack 出的那份。**

跑测试不走 `build.sh`，所以 `GOPROXY` 要自己设（否则默认走 proxy.golang.org，
国内环境常连不上）：

```bash
cd src
export GOCACHE=$PWD/../tools/gocache GOPATH=$PWD/../tools/gopath \
       GOFLAGS=-mod=mod GOPROXY=https://goproxy.cn,direct
go vet ./... && go test ./...     # 75 个用例
```

包里带三个 GeoLite2 库（含 48 MB 的 City，跑省市热加载相关单测要用）。
嫌大可以删 `data/geo/GeoLite2-City.mmdb`，不影响出 fpk。
开发踩坑记录放在 `docs/dev-notes/`。
